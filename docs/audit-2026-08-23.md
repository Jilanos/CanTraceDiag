## Verdict

Le projet a resorbe l'essentiel de la dette signalee en juillet. Les deux P0 sont fermes : la PWA
est validee sur chaque push/PR et l'artefact canonique est documente. La gouvernance Logics est
passee de 47 blocages a 0. Le socle reste sain : lint propre, 166 tests Python verts, 27 tests
Node verts.

PWA reste un assemblage textuel, et elle laisse deja tomber du code produit sans qu'aucun test ne
le detecte.** C'est le seul constat de cet audit qui a un effet utilisateur observable aujourd'hui.

## Constats

### C1 (P0) - Le bouton plein ecran est mort dans la PWA livree

`build-browser.mjs:buildProductAppSource()` concatene une liste de modules codee en dur :

```
["core.js", "import.js", "signals.js", "plot.js", "report.js", "trace.js", "inspector.js", "main.js"]
```

`src/cantracediag/web/js/fullscreen.js` n'y figure pas, alors que `index.html` le charge (ligne 224)
et que le shell HTML recopie dans le site expose bien `#fullscreenBtn` et `#fullscreenNote`
(`site/index.html:38-39`). Verification : `grep -c fullscreen site/browser/product-app.mjs` -> `0`.

Effet : dans l'application deployee, le bouton plein ecran s'affiche, est annonce
`aria-pressed="false"` aux technologies d'assistance, et ne fait rien. Le README l'annonce
pourtant comme une fonctionnalite. Le module etant autonome (il s'enregistre lui-meme sur
`fullscreenBtn`), il n'y a pas d'erreur console : la panne est silencieuse.

Cause racine : la liste de modules est une duplication non verifiee de l'ordre des `<script>` de
`index.html`. Tout nouveau fichier `web/js/*.js` sera silencieusement absent du produit.

Correction :

1. Deriver la liste des modules depuis les balises `<script src="/static/js/...">` de `index.html`
   au lieu de la coder en dur, ou echouer le build si les deux ensembles different.
2. Ajouter un test de build asserant que chaque `web/js/*.js` est represente dans le bundle.
3. Verifier la presence effective du controle plein ecran dans le smoke navigateur.

### C2 (P1) - Le comportement reel du site livre n'est jamais teste automatiquement

`spikes/pwa-local-engine/browser-smoke.mjs` (413 lignes) verifie manifeste, service worker,
cache app-shell et sauvegarde de workspace sur le site genere. Il n'est appele **par aucun
workflow** : seulement par des commandes copiees a la main dans `docs/` et cite comme preuve dans
les documents Logics. La CI se limite a `test -f index.html` / `sw.js`, a des codes HTTP 200 et a
un `Content-Type` de `.mjs`.

Consequence directe : C1 aurait ete invisible aussi longtemps que personne n'ouvrait le site. Les
tests TS couvrent le moteur (`store`, `local-backend`, `workspace`), pas l'assemblage.

Correction : ajouter `browser-smoke.mjs` au job `pwa` de `ci.yml` et a `validate` dans
`release.yml`, et y couvrir au minimum import, trace de courbe, curseurs et plein ecran.

### C3 (P1) - Le produit de production vit toujours sous `spikes/`

L'artefact deploye est construit depuis `spikes/pwa-local-engine/`, avec des dependances croisees
vers `src/cantracediag/web/` (HTML, CSS, JS, SVG). Le repertoire `spikes/pwa-500mb/` est un
benchmark historique de juillet, encore dans l'arbre et dans le contexte Docker.

La consequence n'est pas cosmetique : le shell UI est partage entre le chemin FastAPI et le chemin
PWA sans interface explicite, ce qui est exactement ce qui rend C1 possible. La reecriture par
marqueurs (`replaceBlock` sur `async function api(path, opts) {`, sur un commentaire `// Upload
with progress (AC8)...`, sur `const resp = await fetch("/api/export"`) casse le build a la moindre
retouche de commentaire dans le code source.

Correction : promouvoir la PWA en application de premier rang, extraire une couche UI independante
du transport avec injection d'un client (`ApiClient` FastAPI ou local) au lieu de reecrire la
source, et archiver `spikes/pwa-500mb/`.

### C4 (P2) - Quatre documents Logics figes depuis 31 jours

`logics-manager health` signale `req_007`, `item_017`, `task_017` (PWA SPA local-first) et
`item_021`/`task_021` (migration UI produit, `In progress`) inchanges depuis 31 jours, alors que la
migration PWA est livree et deployee. Quatre demandes restent en `Draft` (`req_007`, `req_011`,
`req_023`, `req_025`) pour du travail deja realise.

Correction : clore ou requalifier ces chaines pour que l'etat Logics reflete la realite du produit.

### C5 (P2) - Supply chain : tags mutables et pinning incoherent

- `Dockerfile` : `node:22-bookworm-slim` et `nginxinc/nginx-unprivileged:1.27-alpine` sont mutables.
- `ci.yml` pin les actions par version exacte (`actions/checkout@v7.0.1`), `release.yml` par majeur
  flottant (`actions/checkout@v7`). Deux politiques dans le meme depot, la moins stricte etant
  celle qui publie et deploie en production.
- Aucune action n'est pinnee par SHA.

Correction : pinner les images par digest, harmoniser sur un pinning par SHA avec Dependabot, en
commencant par `release.yml`.

### C6 (P2) - Le contexte Docker embarque 383 Mo inutiles

`.dockerignore` exclut `.venv` mais pas `.pydeps` (383 Mo), ni `tests/`, `docs/`, `logics/`,
`spikes/pwa-500mb/`. Le `COPY . .` de l'etage de build transfere donc un contexte d'environ 390 Mo
pour produire un site statique de quelques centaines de kilo-octets. Cout : temps de build local et
CI, et surface de fuite si un fichier local sensible atterrit dans l'arbre.

Correction : passer `.dockerignore` en liste d'exclusion explicite (ajouter `.pydeps`, `tests`,
`docs`, `logics`, `tmp`, `.github`, `spikes/pwa-500mb`) ou en allowlist `*` + `!` cibles.

### C7 (P3) - Deprecation Starlette non traitee

`tests/conftest.py:19` declenche `StarletteDeprecationWarning: Using httpx with
starlette.testclient is deprecated; install httpx2 instead`. Deja signale en juillet, toujours
present. Devient une incompatibilite a la prochaine majeure.

Correction : migrer vers `httpx2` dans l'extra `dev` avant que la depreciation ne casse la suite.

### C8 (P3) - `release.yml` valide moins que `ci.yml`

Le job `validate` de la release rejoue les tests TS et le build, mais pas la suite Python, pas le
smoke HTTP statique, pas le smoke MIME de l'image. `ci.yml` s'executant sur `push`, un tag pose sur
un commit deja vert est couvert ; mais la garantie est implicite. Referencer explicitement les
memes controles rendrait la porte de release auto-portante.

## Plan recommande

**Immediat**
1. Inclure `fullscreen.js` dans le bundle PWA et deriver la liste des modules de `index.html` (C1).
2. Brancher `browser-smoke.mjs` sur `ci.yml` et `release.yml` (C2).
3. Ajouter `.pydeps` et les repertoires non necessaires a `.dockerignore` (C6).

**Deux prochaines iterations**
4. Extraire la couche UI derriere une interface de transport, supprimer `replaceBlock` (C3).
5. Sortir la PWA de `spikes/`, archiver `spikes/pwa-500mb/` (C3).
6. Clore les chaines Logics figees (C4).

**Ensuite**
7. Pinner images par digest et actions par SHA, harmoniser `ci.yml` / `release.yml` (C5, C8).
8. Migrer vers `httpx2` (C7).
9. Decomposer progressivement `api.py` et `store.py` par domaine (dette de juillet inchangee).

## Points forts

- 166 tests Python + 27 tests Node verts, lint propre, aucune derive de build.
- Modele de securite local-first explicite et teste (`security.py` : allowlist d'hotes, defense
  anti-rebinding DNS, token de session, plafond d'upload, import serveur desactive hors loopback).
- En-tetes de securite HTTP complets sur le site heberge, Nginx non privilegie.
- Release verifiee : format du tag, ancetre de `main`, SBOM, provenance, labels OCI, deploiement par
  digest de tag et verification de sante.
- Gouvernance Logics assainie : 0 blocage sur 137 documents de workflow.
- Sorties de build correctement exclues du depot (`browser/`, `site/`).
